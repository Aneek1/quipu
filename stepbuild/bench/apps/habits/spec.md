A habit tracker where each habit has an integer `id` assigned by the server (ids are never reused, even after a delete), a required `name` (a string that is not empty after trimming whitespace) and a `description` (a string that defaults to an empty string when it is left out); every new app instance starts with no items. The API has five JSON endpoints for habits and two for check-ins: `GET /api/habits` returns all habits as a JSON array; `POST /api/habits` creates a habit from a JSON body with `name` and optional `description` and returns the new habit with its `id` and status 201; `GET /api/habits/<id>` returns one habit; `PUT /api/habits/<id>` updates a habit and returns the updated habit with status 200, where PUT accepts any subset of the fields; fields left out keep their values; a field that is sent follows the same rules as on create (so an empty `name` is 400); `DELETE /api/habits/<id>` deletes a habit (and its check-ins) and returns 200 or 204. `POST /api/habits/<id>/checkins` records that the habit was done on a day, from a JSON body with a required `date` (a string in the form `YYYY-MM-DD` that is a real calendar date, such as `"2026-09-28"`), and returns the check-in, an object with its own integer `id`, the `habit_id` and the `date` (check-in ids come from one counter shared by all habits, so no two check-ins share an `id`); a check-in is idempotent per habit per day: the first check-in for a habit and date returns status 201, and sending the same habit and date again returns status 200 with the same check-in (same `id`) and does not add a second one. `GET /api/habits/<id>/checkins` returns that habit's check-ins as a JSON array. The validation rules, each rejected with status 400 and a JSON body with an `error` key, are: `name` missing, not a string, or empty after trimming whitespace; `description` sent but not a string; a check-in `date` missing or not a string, and the date must be exactly 10 characters, `YYYY-MM-DD` with a two-digit month and day and a real calendar date, so `"2026-9-28"` and `"2026-02-30"` are 400. A field sent as `null` counts as sent, so `null` for a field is 400. Any request for a habit `id` that does not exist returns 404, including both check-in endpoints. The page shows the list of habits (name and description) with a delete button on each and a form to add a new habit.
